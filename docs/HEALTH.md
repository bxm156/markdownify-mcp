# Health checks and LiteLLM 1.104

LiteLLM 1.104.0's MCPServerManager.health_check_server opens an MCPClient session with static headers and no user identity. Its callback is a no-op; successful MCP initialization is marked healthy. It does not call /readyz or fetch detailed health metrics. The per-user signer is not part of this health path.

Source: [LiteLLM 1.104 manager](https://github.com/BerriAI/litellm/blob/10444df3a0173a99ab4e4858ce6777f31530e6c5/litellm/proxy/_experimental/mcp_server/mcp_server_manager.py). The integration test uses the actual installed 1.104.0 MCPClient.run_with_session path.

## Public readiness and restricted MCP probes

GET or HEAD /livez (alias /healthz) returns 200 `{"status":"ok"}` whenever the process is serving; point container HEALTHCHECK and liveness probes here so a full disk does not cause restart loops. GET or HEAD /readyz returns HTTP 200 only after initialization, while accepting work, with writable storage/free space, an available converter executable and a working audit sink. Otherwise it returns 503. Its public body contains only status, ready and boolean checks (initialized, accepting_work, storage.writable, converter.available, audit.available); free space, memory, uptime and check time are reserved for get_service_health. An in-flight check is shared by concurrent requests, and completed checks are cached for two seconds after they settle. Storage is tested with a small write/delete probe and statfs. A check that has not finished within five seconds (for example on a hung network mount) reports not ready immediately instead of hanging: the component that timed out (storage or converter) is reported unavailable, while a check that already finished keeps its result. No new filesystem probe starts until the hung call returns, so /readyz stays 503 (and /livez stays 200) for as long as the filesystem is wedged, and get_service_health keeps reporting the original checked_at. Converter availability means an executable file was found, not that all Python dependencies or document conversions work. Health and the converter share one lookup and the converter runs the file health found: `MARKITDOWN_PATH`, else the project `.venv`, else a bare `markitdown` searched on PATH (empty PATH entries are skipped). On Unix the file must be a regular file with execute permission. Windows has no execute bit, so there the file only has to exist, but it must end in `.exe` or `.com`, because the converter starts it without a shell and Windows cannot run `.cmd` or `.bat` files that way. A bare name is tried with each PATHEXT suffix in that set (`.COM;.EXE` when PATHEXT is unset; empty entries, such as from a trailing `;`, are ignored), so a `markitdown.cmd` shim or an extensionless file is reported unavailable rather than counted and then failing at conversion time.

audit.available becomes false when an audit write fails, because every job operation then fails with `AUDIT_UNAVAILABLE`, and becomes true again on the next successful write. A record the audit logger rejects before touching storage (invalid metadata) fails only that operation and does not change audit.available. Health checks never write an audit record. While the sink is failing, a check also runs a recovery probe that opens the audit log for append without writing and requires free space, within the same five-second bound, so a replica that readiness has taken out of service can recover without traffic. The probe cannot detect failures that only appear when bytes are written (EIO, quotas), so to keep readiness from flapping it backs off and must pass twice: the first probe runs at once, the wait after each probe starts at 2 s and doubles up to 60 s, and audit.available returns only after two consecutive passing probes with no failed write in between. The backoff carries over when a write fails again after a probe-based recovery and resets only on a successful write. Each transition is logged once to stderr as a single-line JSON event, `audit_sink_unavailable` (errno-style `code` only) or `audit_sink_recovered` (`via`: `write` or `probe`). Until a write fails, audit.available is true. See [audited events](MULTITENANT.md#audited-events).

In JWT mode only, requests with no Authorization header may perform initialize, notifications/initialized and ping on /mcp. They are gated by the same readiness check and receive no owner, tool capabilities or authenticated access. Any request carrying an Authorization header is verified first: a missing-sub, expired or otherwise invalid JWT, or an upload grant, is rejected with 401 and `WWW-Authenticate: Bearer` on every method, including initialize and ping, so a user session with a broken JWKS, issuer or audience setup now fails at connect instead of appearing connected. The header-less LiteLLM health probe and /readyz cannot detect JWT misconfiguration. Batch requests and all other methods still require authentication. Tools/list, tools/call, resources and prompts remain protected. Registry mode continues requiring authentication for MCP probes.

Keep Host/Origin checks and TLS enabled. /livez, /healthz and /readyz accept any Host and Origin so orchestrator probes (which send the pod IP as Host) work; all other routes still enforce the allowlist. No shared health principal, fallback user, long-lived monitoring key or job ownership is created. Public probes expose only the readiness verdict, not user identities, job counts, reservations, capacity metrics, paths or errors.

## Private agent metrics

Use get_service_health({}) with the normal authenticated agent and its per-tool JWT scope. It returns detailed readiness (checked_at, uptime_seconds, memory_rss_bytes, storage free_bytes, converter.check, which is "custom" for test converters and "executable" otherwise, and audit.available) plus:

- own_jobs: counts for the caller's job states, including retained expired tombstones.
- own_reserved_bytes: the caller's current input-plus-maximum-output reservation, using the same non-expired-state accounting as admission.
- limits: configured global/tenant/agent job, storage and concurrency caps (agent caps include any [operator override](MULTITENANT.md#operator-quota-overrides) for the caller, flagged by agent_override), per-file/output limits, and effective: the tightest jobs, reserved_bytes and concurrency caps that apply to the caller.
- cleanup: last_sweep_at, when the latest retention sweep finished, plus own_jobs_failed_last_sweep and own_jobs_pending_retry, counting only the caller's jobs whose expiry erasure or tombstone removal failed and will be retried. Failures caused by other users' jobs are never included, and cleanup failures do not fail readiness. Operators get service-wide totals from stderr; see [MULTITENANT.md](MULTITENANT.md#inspecting-and-purging-a-retired-users-artifacts).

There is no foreign-user usage, job ID or tenant list. Global limits are configuration, not global usage. When JWT tenant and agent IDs both equal the user ID, both caps constrain that user. A full quota or queued work is normal capacity pressure and does not make readiness fail. Quotas exclude metadata/index/audit overhead; disk free space is a filesystem metric, not reserved storage.

This check does not inspect LiteLLM admission, JWT signing configuration, public TLS, audit log retention or export, parser quality or end-to-end conversion success. Use real conversion/isolated-agent tests for those checks.

## Reproduce the upstream probe locally

Build the server and make MarkItDown available on PATH or set MARKITDOWN_PATH, then use an isolated Python environment:

```sh
bun run build:remote
python -m pip install 'litellm[mcp]==1.104.0'
python scripts/litellm-health-smoke.py
```

The test starts a compiled Node JWT-mode service and runs LiteLLM's real `MCPClient.run_with_session` initialization path anonymously. It additionally sends `ping`, so it is a superset of LiteLLM's no-op health callback (which only initializes). It then checks real readiness and confirms anonymous discovery is rejected with a real HTTP 401 status error from LiteLLM's httpx2 client (a timeout, transport error or any other status fails the test; message text is never matched). The script first runs a built-in regression self-test of that classifier; `python scripts/litellm-health-smoke.py --self-test` runs only that part. It supplies no user token and does not contact a real gateway. CI runs this alongside authenticated conversion and isolation checks.
